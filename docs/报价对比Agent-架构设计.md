# 报价对比 Agent —— 架构设计与基础设施方案（v2）

> 目标：用户在前端上传 N 个供应商报价单（Excel/Word/PDF/扫描件），Agent 按统一报价结构完成识别、匹配，直接呈现比价界面；用户在查看比价的过程中顺手修正问题；LLM 在机械金额对比之上提供综合对比建议。
> v2 修订（2026-09-08 晚），采纳 7 项决策：全层级金额字段；取消确认前置门禁；其它工艺兜底+新工艺上报；LLM 职责边界实测可调；前后端完整项目；LLM 综合对比层；主数据管理界面。
> 配套：《quote_schema.json v1.1》《报价结构说明.md》《原子工艺清单v2.xlsx》。

---

## 一、系统形态：前后端完整项目

```
┌──────────────────────────── 前端（React SPA）──────────────────────────┐
│ ① 对比任务发起页（上传文件、选品类）  ② 处理进度页（实时刷新）            │
│ ③ 比价界面（LLM建议区 + 层级金额对比表 + 加工费维度抽屉 + 就地编辑）      │
│ ④ 主数据管理页（品类/原子/别名/抽屉/供应商 CRUD）                        │
└──────────────────────────────┬────────────────────────────────────────┘
                               │ REST API + SSE（进度推送）
┌──────────────────────────────▼────────────────────────────────────────┐
│ 后端（Python / FastAPI）                                               │
│  任务编排 → 解析流水线（五段） → 机械对比引擎 → LLM 综合对比层            │
│  主数据服务 / 修正回写服务 / 别名回流服务 / 新工艺建议队列                │
├────────────────────────────────────────────────────────────────────────┤
│ 存储：SQLite（主数据+业务数据） + 文件系统（原始文件归档 + JSON 快照）     │
└────────────────────────────────────────────────────────────────────────┘
```

技术选型建议（可替换，非约束）：FastAPI + SQLite 起步；前端 React + TanStack Query + 可下钻表格组件；任务进度用 SSE（Server-Sent Events）推送，比 WebSocket 简单够用；文件解析与 LLM 调用放后台任务队列（如 arq/dramatiq，甚至 FastAPI BackgroundTasks 起步）。

## 二、用户主流程（对应前端四个页面）

```
① 发起对比：上传 N 个文件 + 填项目名称（★ 无需选品类，品类由 Agent 自动判定）
        ↓ 创建对比任务，每个文件一个解析子任务
② 处理进度：进度页实时显示每个文件的处理段（查重→接入→解析→匹配→校验）
        ↓ 全部完成（或部分失败，失败项标注原因）
③ 比价界面：★ 用户看到的第一个结果界面就是比价
   ┌─ 顶部：LLM 综合对比建议区（见 §五）
   ├─ 中部：层级金额对比表（模块合计横向对比，+/− 号逐层折叠/展开明细）
   ├─ 加工费专区：维度抽屉切换（工艺域/工艺阶段/工艺类别三个独立维度 + 自定义抽屉）
   ├─ 警示徽标：低置信度 / 勾稽异常 / 未匹配 / 新工艺候选 / 品类判定存疑
   └─ 就地编辑：改金额、改原子映射、改品类、补字段，保存即生效
        ↓
④ 新工艺决策：is_new_process 条目弹出决策卡片 → 新增原子 or 归并现有
```

**不再有独立的"确认台"前置页面**。人工介入全部发生在比价界面内：问题是徽标，不是门禁；修正是顺手，不是流程。后台仍保留修正队列 API（供"只看待办"的用户习惯），但它只是比价界面警示项的过滤视图。

## 三、解析流水线（五段，JSON 先行）

```
文件接入(脚本) → 版面理解(LLM+脚本) → 语义映射(脚本优先,LLM兜底) → 校验(脚本) → 落库(脚本)
                        全程在 quote_schema.json v1.1 的 JSON 结构上处理
```

**⓪ 查重（纯脚本，解析前置门禁）**：文件入库先算哈希，与历史文件比对——**已解析过的文件直接复用历史解析结果**，不重复跑流水线（用户可在发起页选择"强制重新解析"覆盖）。

**① 文件接入层（纯脚本）**：Excel(openpyxl) / Word(python-docx) / PDF文字版(pdfplumber) / 扫描件(OCR) → 统一中间表示 IR（文本块/表格行序列，带坐标）。同时归档原文件。

**② 版面理解层（LLM 为主，脚本交叉验证）**：LLM 直接从 IR 产出结构化字段值（**含金额数字**）——LLM 理解版面语义的产出是主要数据源。脚本在能做的地方做**独立交叉验证**：规则定位到的金额、明细加总、IR 原文坐标比对，与 LLM 产出对账；**一致 → high 置信；不一致 → 打标"交叉验证异常"，两个值都保留进比价界面供人裁定**（脚本不保证能给出结果，给出也不保证可靠，所以它只验证不独裁）。

本段同时完成**品类自动判定**：LLM 依据报价内容（零件名称、材料、工艺用词）判定品类并给出置信度，写入 `basic.category`；置信度低时打"品类存疑"徽标，用户在比价界面可一键改品类（改后自动触发该单原子映射重跑）。

**③ 语义映射层（三级流水）**：
```
加工费条目原文
 ├─ L1 别名精确匹配（脚本）→ 命中唯一 → confidence=high ✅
 ├─ L2 LLM 语义匹配（约束生成：只能从该品类候选原子子集选编码）
 │    → 多编码 = 打包项（生成组合指纹）
 │    → 判定为清单外工艺 → atom_code=null + is_new_process=true
 └─ L3 完全无法判断 → atom_code=null, confidence=low
    ★ 任何级别金额都保留落库，匹配失败损失的只是对比粒度
```
非加工费条目用同义词表+规则映射费用类型，归不进任何模块的进 `other`（说明必填）。

**④ 校验层（纯脚本）**：Schema 校验 / 枚举校验（原子编码、币种、item_type）/ 勾稽校验（未税合计链条允差 ±0.01 或 ±1%；**模块内部：total 应 ≥ Σitems，小于则判异常**）/ 交叉验证异常汇总 / 异常值检测。**所有校验失败只打标不阻断**，照常进比价。

**⑤ 落库（纯脚本）**：JSON 快照原样存档 + 拍平派生写关系表（quote / quote_line / tooling_line）。模块 total 字段同样落库（`quote_line` 增加 module_total 行类型或 quote 表增加各模块合计列——实现时二选一，推荐后者：quote 表加 6 个模块合计列 + tooling 合计列，层级对比查询不用聚合）。

**LLM 职责边界说明（采纳决策 ④）**：上述分工是初始假设，**不是约束**。开发中每段的 LLM/脚本取舍以 `eval_replay` 实测命中率为准调整——比如②段交叉验证的脚本覆盖率做到多高、L2 调用率随别名库成熟下降后是否收紧 LLM 使用，都由评估数据驱动，不由设计文档锁死。

## 五、LLM 综合对比层（机械对比之上的决策建议）

机械对比（纯脚本，SQL 聚合）产出数字表格；**LLM 综合对比层在其上生成建议内容**，展示在比价界面顶部：

```
输入（全部结构化数据，不让 LLM 碰原始文件）：
  - 各家 summary（最终含税单价、各模块合计）
  - 加工费维度抽屉汇总 + 打包指纹对齐结果
  - 警示项集合（勾稽异常、低置信度、新工艺候选）
  - 模治具费对比
输出（前端"综合建议区"展示，明确标注 AI 生成）：
  1. 推荐排序 + 一句话理由（"B 总价最低但表面处理依赖打包项，明细待核"）
  2. 关键差异解读（工艺路线差异：A 用压铸、B 用 CNC——结构性差异而非价差）
  3. 异常提醒（"C 的损管利税占比 28%，显著高于其他家 12-15%"）
  4. 议价抓手建议（"材料费差异主要来自铝材单价假设，可要求 B 澄清"）
  5. 数据质量声明（"本次对比含 3 条低置信度匹配，建议优先核实"）
```

硬规矩：**LLM 只能引用输入数据中的数字，输出前由脚本回检**——把建议文本中的金额数字与机械对比结果对账，对不上就标记或重生成。综合建议层的 prompt 与输出全部落 parse_log。

## 六、新工艺发现与主数据回流闭环

```
L2/L3 中 LLM 判定"清单外工艺"
  → 条目 atom_code=null, is_new_process=true
  → 写入 new_atom_suggestion 队列（含 LLM 建议的名称/域/阶段归属）
  → 前端比价界面弹出决策卡片："发现新工艺『XX』，出现 2 次"
     ├─ [新增原子] → atom 表追加（域内顺序取新编码）+ 别名自动收录 + 条目改挂新编码
     ├─ [归并现有] → 用户选择现有原子 → 原文写入 atom_alias（来源=人工回流）
     └─ [忽略]     → 条目保持未匹配，不再提示本次任务
所有人工修正（改选原子/改金额）同步触发别名回流
```

这是命中率从 70% → 90%+ 的唯一机制，也是原子清单持续运营的生命线。

```
第1步  建库 + import_master_data（含内置抽屉初始化）
第2步  ingest + normalize（先 Excel）+ persist       → 骨架可跑

第4步  compare_engine + 后端 API + 比价界面（最小版）  → 第一个可用闭环 ★

第7步  correction_service + 就地编辑 + 别名回流
```

## 十一、关键不变量（无论怎么迭代都要守住）

1. **金额永不受损**：任何匹配失败只损失对比粒度，金额永远落库、永远可见
2. **层级金额可信**：模块 total 与 Σitems 的取值优先级固定，勾稽失败打标不隐藏
3. **LLM 数字回检**：综合建议层的所有金额必须与机械对比结果对账
4. **证据链完整**：每条数据可回溯到原文件原文位置
5. **主数据变更留痕**：原子新增/别名回流/抽屉变更都有来源与时间戳
