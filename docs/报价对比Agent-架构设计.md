# 报价对比 Agent —— 架构设计与基础设施方案（v2）

> 目标：用户在前端上传 N 个供应商报价单（Excel/Word/PDF/扫描件），Agent 按统一报价结构完成识别、匹配，直接呈现比价界面；用户在查看比价的过程中顺手修正问题；LLM 在机械金额对比之上提供综合分析。
> v2 修订（2026-09-08 晚），采纳 7 项决策：全层级金额字段；取消确认前置门禁；其它工艺兜底+新工艺上报；LLM 职责边界实测可调；前后端完整项目；LLM 综合分析层；主数据管理界面。
> v3 修订：比价界面**取消旧版「AI 建议」模块，改为顶部「AI 分析」模块**（表格化：含税单价/优势/劣势/风险/建议 + 9 个可展开子维度）；解析阶段新增 **`other_info`「其它信息」**字段作为 AI 分析的重要补充信息源；前端导航改为**左侧菜单栏**。
> v3.1 修订（解析准确性整改）：金额缺失契约化（未印出填 `null`，禁 0 占位/禁推算）；L1 溯源校验**锚定 IR 原文**并新增 `raw_text_not_verbatim` / `amount_not_in_ir`；重试留证 + 零进展熔断（见 §三 ②-b）；勾稽新增 `amount_missing` 标记。
> 配套：《quote_schema.json v1.1》《报价结构说明.md》《原子工艺清单v2.xlsx》。

## 一、系统形态：前后端完整项目

```
┌──────────────────────────── 前端（React SPA）──────────────────────────┐
│ ① 对比任务发起页（上传文件、选品类）  ② 处理进度页（实时刷新）            │
│ ③ 比价界面（AI 分析模块 + 层级金额对比表 + 加工费维度抽屉 + 就地编辑）  │
│ ④ 主数据管理页（品类/原子/别名/抽屉/供应商 CRUD）                        │
└──────────────────────────────┬────────────────────────────────────────┘
                               │ REST API + SSE（进度推送）
┌──────────────────────────────▼────────────────────────────────────────┐
│ 后端（Python / FastAPI）                                               │
│  任务编排 → 解析流水线（五段） → 机械对比引擎 → LLM 综合对比层            │
│  主数据服务 / 修正回写服务 / 别名回流服务 / 新工艺建议队列                │
├────────────────────────────────────────────────────────────────────────┤
│ 存储：SQLite（主数据+业务数据） + 文件系统（原始文件归档 + JSON 快照）     │
└────────────────────────────────────────────────────────────────────────┘
```

技术选型建议（可替换，非约束）：FastAPI + SQLite 起步；前端 React + TanStack Query + 可下钻表格组件；任务进度用 SSE（Server-Sent Events）推送，比 WebSocket 简单够用；文件解析与 LLM 调用放后台任务队列（如 arq/dramatiq，甚至 FastAPI BackgroundTasks 起步）。

## 二、用户主流程（对应前端四个页面）

```
① 发起对比：上传 N 个文件 + 填项目名称（★ 无需选品类，品类由 Agent 自动判定）
        ↓ 创建对比任务，每个文件一个解析子任务
② 处理进度：进度页实时显示每个文件的处理段（查重→接入→解析→匹配→校验）
        ↓ 全部完成（或部分失败，失败项标注原因）
③ 比价界面：★ 用户看到的第一个结果界面就是比价
   ┌─ 顶部：AI 分析模块（见 §五）
   ├─ 中部：层级金额对比表（模块合计横向对比，+/− 号逐层折叠/展开明细）
   ├─ 加工费专区：维度抽屉切换（工艺域/工艺阶段/工艺类别三个独立维度 + 自定义抽屉）
   ├─ 警示徽标：低置信度 / 勾稽异常 / 未匹配 / 新工艺候选 / 品类判定存疑
   └─ 就地编辑：改金额、改原子映射、改品类、补字段，保存即生效
        ↓
④ 新工艺决策：is_new_process 条目弹出决策卡片 → 新增原子 or 归并现有
```

**不再有独立的"确认台"前置页面**。人工介入全部发生在比价界面内：问题是徽标，不是门禁；修正是顺手，不是流程。后台仍保留修正队列 API（供"只看待办"的用户习惯），但它只是比价界面警示项的过滤视图。

## 三、解析流水线（五段，JSON 先行）

```
文件接入(脚本) → 版面理解(LLM+脚本) → 语义映射(脚本优先,LLM兜底) → 校验(脚本) → 落库(脚本)
                        全程在 quote_schema.json v1.1 的 JSON 结构上处理
```

**⓪ 查重（纯脚本，解析前置门禁）**：文件入库先算哈希，与历史文件比对——**已解析过的文件直接复用历史解析结果**，不重复跑流水线（用户可在发起页选择"强制重新解析"覆盖）。

**① 文件接入层（纯脚本）**：Excel(openpyxl) / Word(python-docx) / PDF文字版(pdfplumber) / 扫描件(OCR) → 统一中间表示 IR（文本块/表格行序列，带坐标）。同时归档原文件。

**② 版面理解层（LLM 为主，脚本交叉验证）**：LLM 直接从 IR 产出结构化字段值（**含金额数字**）——LLM 理解版面语义的产出是主要数据源。脚本在能做的地方做**独立交叉验证**：规则定位到的金额、明细加总、IR 原文坐标比对，与 LLM 产出对账；**一致 → high 置信；不一致 → 打标"交叉验证异常"，两个值都保留进比价界面供人裁定**（脚本不保证能给出结果，给出也不保证可靠，所以它只验证不独裁）。

本段同时完成**品类自动判定**：LLM 依据报价内容（零件名称、材料、工艺用词）判定品类并给出置信度，写入 `basic.category`；置信度低时打"品类存疑"徽标，用户在比价界面可一键改品类（改后自动触发该单原子映射重跑）。

**②-b 解析期三层校验与重试闭环（脚本，防幻觉闸门）**：LLM 输出必须先过三道脚本闸门，问题按 `blame` 分流——**`blame=A` 才触发重试，`blame=B` 只打标**：

| 层 | 校验项 | 失败处理 |
|---|---|---|
| **L0 结构** | Draft7 信封 + 单 offer schema：类型 / 必填 / 枚举（币种、item_type、原子编码） | `schema_invalid` 反馈重试；3 轮仍不过 → 该文件标失败 |
| **L1 溯源** | 金额必须能在**自身 `evidence.raw_text`** 中找到；`evidence.location` 必须落在 IR 范围内；`raw_text` 必须是**原文照抄**（等于 location、纯坐标样式、IR 序列化片段如 `8:1\|9:28\|10:0.96` → `raw_text_not_verbatim`）；`amount_not_in_evidence`（抄错单元格）/ `amount_not_in_ir`（**金额在整张单据任何单元格中都不存在 = 编造**） | `traceability` 反馈重试；3 轮仍不过 → 该文件标失败 |
| **L2 勾稽** | 模块 total vs Σitems、未税合计链条、税额=税率×未税；明细金额缺失（null）记 `amount_missing` | 只写 `attempts.l2_issues` + 落库打标，**不打断** |

- **锚定 IR，而不是锚定模型自己的输出**：L1 的"金额有出处"判据取自脚本侧 IR 原文（`_ir_numeric_values`），**不是** LLM 自己填的 `raw_text`——否则模型把编造值同时写进金额与 `raw_text` 就能自证清白（这正是本轮回归暴露的真实故障：模型把 IR 序列化片段 `8:1|9:28|10:0.96` 当 `raw_text` 回填，并据此"证明"自己算出的 26.88）。拿不到 IR 文本时按保守策略放行，避免不支持格式整单误杀。
- **L1 与 L0 同轮计算**：schema 报错会掩盖真正的首因（如"填 0 占位"背后藏着的编造金额），L0 失败时 L1 结果照样入档。
- **金额缺失的契约**：Schema 中明细/合计金额为 `["number","null"]`，单据未印出必须填 `null` 并把要素原文留在 `note`——**禁 0 占位、禁推算**（详见《报价结构说明.md》第三节）。
- **重试留证 + 零进展熔断**：每轮原始输出与校验结果落盘 `backend/data/llm_trace/{file_hash}_r{n}.json`（`LLM_TRACE=0` 关闭）；若某轮输出与上一轮**完全一致**（模型对 retry 反馈零响应），立即终止、不再空烧剩余轮次；`LLMValidateError` 消息带逐轮摘要（每轮失败类型 + schema/溯源错误数）。
- **反馈模板化**：`retry_feedback.md` 按失败类型（`schema_invalid` / `traceability` / `json_unparseable`）给出可执行修法，当轮错误清单填入模板后追加进对话，避免只丢一句"输出有误"。

**③ 语义映射层（三级流水）**：
```
加工费条目原文
 ├─ L1 别名精确匹配（脚本）→ 命中唯一 → confidence=high ✅
 ├─ L2 LLM 语义匹配（约束生成：只能从该品类候选原子子集选编码）
 │    → 多编码 = 打包项（生成组合指纹）
 │    → 判定为清单外工艺 → atom_code=null + is_new_process=true
 └─ L3 完全无法判断 → atom_code=null, confidence=low
    ★ 任何级别金额都保留落库，匹配失败损失的只是对比粒度
```
非加工费条目用同义词表+规则映射费用类型，归不进任何模块的进 `other`（说明必填）。

**④ 校验层（纯脚本）**：Schema 校验 / 枚举校验（原子编码、币种、item_type）/ 勾稽校验（未税合计链条允差 ±0.01 或 ±1%；**模块内部：total 应 ≥ Σitems，小于则判异常**）/ 交叉验证异常汇总 / 异常值检测。**所有校验失败只打标不阻断**，照常进比价。

**⑤ 落库（纯脚本）**：JSON 快照原样存档 + 拍平派生写关系表（quote / quote_line / tooling_line）。模块 total 字段同样落库（`quote_line` 增加 module_total 行类型或 quote 表增加各模块合计列——实现时二选一，推荐后者：quote 表加 6 个模块合计列 + tooling 合计列，层级对比查询不用聚合）。

**LLM 职责边界说明（采纳决策 ④）**：上述分工是初始假设，**不是约束**。开发中每段的 LLM/脚本取舍以 `eval_replay` 实测命中率为准调整——比如②段交叉验证的脚本覆盖率做到多高、L2 调用率随别名库成熟下降后是否收紧 LLM 使用，都由评估数据驱动，不由设计文档锁死。

## 五、LLM 综合分析层（机械对比之上的决策建议）

机械对比（纯脚本，SQL 聚合）产出数字表格；**LLM 综合分析层在其上生成对比论断**，展示在比价界面最顶部的「AI 分析」模块：

```
输入（全部结构化数据，不让 LLM 碰原始文件）：
  - 各家 supplier 头（最终含税单价、排名、勾稽结论、警示 flags）
  - 我方比对基线 summary_rows（六大模块合计 + 最终价）
  - quote_line 明细（按模块/原子工艺拍平，含金额与原子编码）
  - 加工费维度抽屉汇总 + 打包指纹对齐结果（drawers）
  - 模治具费（tooling）与校验警示集合（warnings）
  - 品类判定结果（category）
  - ★ 各家解析阶段的 other_info「其它信息」（工艺路线、付款/账期、运输、模具条款等补充原文归纳）
输出（JSON，渲染为「AI 分析」模块的对比表）：
  **列顺序与「报价对比」表的供应商列完全一致**（同一份 comparison.suppliers 顺序，即报价单 id 升序；
  价格次序只由 price_rank/is_lowest 表达），每列一家供应商：
  1. 含税单价（最低/最高标签由机械对比结果加，不信任 LLM）
  2. 优势 / 劣势 / 风险（各 ≤25 字）
     └ 各自可展开 3 个固定子维度（与「报价对比」一致的 +/− 号与底色）：
        优势：成本/材料、工艺/质量、商务/交付
        劣势：成本/费用、材料/工艺、商务/交付
        风险：质量/合规风险、成本/商务风险、资金/交付风险
  3. 建议（采购动作）
```

**触发时机**（由输入指纹 `signature` 决定，指纹 = prompt 版本 + 结构化输入的哈希）：

| 场景 | 行为 |
|---|---|
| 文件解析完毕首次进入比价页 | 自动触发（该指纹下无任何分析记录） |
| 刷新页面 / 重复进入 | 不触发（指纹已有记录，`auto_run=false`） |
| 新增供应商后再进比价页 | 重新触发（供应商集合变化 → 指纹变化） |
| 用户点「重新分析」 | 手动强制触发，忽略指纹复用 |

推理过程中前端展示占位模块（动画 + 阶段文案 + 已耗时），期间轮询查询态接口，完成后自动替换为表格。

硬规矩：**LLM 只能引用输入数据中的数字，输出前由脚本回检**——把输出文本中的金额数字与机械对比结果对账，对不上标记为"部分数字待核对"（`check_status=mismatch`），并在回归测试中持续跟踪。分析 prompt 与输出全部落 `parse_log`。

## 六、新工艺发现与主数据回流闭环

```
L2/L3 中 LLM 判定"清单外工艺"
  → 条目 atom_code=null, is_new_process=true
  → 写入 new_atom_suggestion 队列（含 LLM 建议的名称/域/阶段归属）
  → 前端比价界面弹出决策卡片："发现新工艺『XX』，出现 2 次"
     ├─ [新增原子] → atom 表追加（域内顺序取新编码）+ 别名自动收录 + 条目改挂新编码
     ├─ [归并现有] → 用户选择现有原子 → 原文写入 atom_alias（来源=人工回流）
     └─ [忽略]     → 条目保持未匹配，不再提示本次任务
所有人工修正（改选原子/改金额）同步触发别名回流
```

这是命中率从 70% → 90%+ 的唯一机制，也是原子清单持续运营的生命线。


## 十一、关键不变量（无论怎么迭代都要守住）

1. **金额永不受损**：任何匹配失败只损失对比粒度，金额永远落库、永远可见
2. **层级金额可信**：模块 total 与 Σitems 的取值优先级固定，勾稽失败打标不隐藏
3. **LLM 数字回检**：AI 分析模块的所有金额必须与机械对比结果对账
4. **证据链完整**：每条数据可回溯到原文件原文位置
5. **主数据变更留痕**：原子新增/别名回流/抽屉变更都有来源与时间戳
