# 报价结构说明（定稿 v1.1）

> 配套文件：`quote_schema.json`（机器可校验的正式定义）。本文档面向人阅读，解释每个设计决策。
> v1.1 更新（2026-09-08 晚）：全层级金额字段；其它工艺兜底与新工艺上报；取消"先确认后比价"门禁，改为比价界面内即时修正。

---

## 一、数据流总原则：JSON 先行，落库殿后

```
LLM 解析输出 (JSON)
   → 按 quote_schema.json 校验
   → 加工费原子匹配、指纹生成、勾稽计算（全程在 JSON 上处理）
   → 直接进入比价界面（★ 无人工确认前置环节）
   → 用户在比价界面中发现问题 → 就地修改（改的还是这份 JSON）
   → JSON 原样存档（raw_json，审计与重解析用）
   → 同时拍平派生写入关系表（quote / quote_line / tooling_line，供对比查询）
```

JSON 是**处理的基准形态**，关系表是**查询的索引形态**。

## 二、全层级金额原则（v1.1 核心变更）

供应商可能只报模块总价而没有明细（如"包装运输费 0.08 元/pcs"一条，包装、运输拆不开）。因此**每个层级都有自己的金额字段**：

```
最终含税单价 final_unit_price_taxed          ← 产品单价级总额（对比第一基准）
├─ materials.total          材料费合计        ─┐
├─ processing.total         加工费合计         │
├─ inspection.total         检验费合计         │ 模块级合计：都有 total 字段
├─ packaging_transport.total 包装运输费合计    │ 供应商只报模块价时 items 为空
├─ sga_tax.total            损管利税合计       │
├─ other.total              其他费用合计      ─┘
│   └─ items[]              各模块明细条目（有就填，没有就空）
└─ tooling.total            模治具总合计（元/项，一次性）
    ├─ molds.total / items[]     模具费合计 + 明细
    ├─ fixtures.total / items[]  治具费合计 + 明细
    └─ stencils.total / items[]  钢网费合计 + 明细
```

**total 与 items 的取值规则**：
- 供应商只报合计 → 填 total，items 为空数组
- 供应商报了明细没报合计 → total 留 null，展示层按 Σitems 计算显示
- 两者都有 → **模块合计应 ≥ 明细之和**（供应商可能在合计中包含未逐项列出的内容，不等于明细之和是常态）；若合计 < 明细之和则判为勾稽异常。对比取值优先级：total > Σitems

**对比界面按层级展开**：第一屏只看各模块合计的横向对比；每个带明细的行都有 **+/− 折叠/展开按钮**，用户按需展开某模块看明细条目；加工费模块可再按维度抽屉切换视角（见第六节）。

## 三、生产加工费模块（统一结构，全品类通用）

条目字段：`名称(原文) / 金额(元/pcs) / 原子编码 / is_new_process / 打包标志 / 候选原子列表 / 组合指纹 / 拆分方式 / 置信度 / 匹配路径 / 确认状态 / 说明 / 原文出处`

- **不做每品类独立结构**；品类差异由原子清单的品类标签表达。
- 金额无论匹配与否永远保留；未匹配 = `atom_code: null`。
- **其它工艺兜底**：工艺不在清单中时，`atom_code = AT-QT-001`（其它工艺）+ `is_new_process = true`，金额正常参与加工费合计与总价勾稽，不因"清单外"而丢失。
- **新工艺上报**：`is_new_process = true` 的条目触发 Agent 在前端向用户提问"是否新增原子工艺"（详见架构文档 §六）。
- 打包项：`bundle_flag=true`，按组合指纹跨供应商对齐，不强行估拆。

## 四、损管利税模块

损耗、管理费、利润、税费合为一个模块 `sga_tax`，条目用 `item_type` 标注；供应商合并报价时一条条目即可，不强拆；按百分比报的用 `rate` 保留原费率；税费条目 `rate` 必填。模块只有总价时同样只填 `sga_tax.total`。

## 五、勾稽规则（校验层依据）

```
模块合计取值优先级：模块 total 字段 > Σ 模块 items
模块内部勾稽：模块 total ≥ Σ 模块 items（合计可含未单列内容；total < Σitems 判为异常）
未税合计 untaxed_total  = Σ 六个模块合计（排除 sga_tax 中 item_type=税费 的金额）
含税合计 taxed_total    = untaxed_total + tax_amount
最终含税单价            = taxed_total − discount
```

- 勾稽允差 ±0.01 元或 ±1%。
- **勾稽失败不阻断流程**：`calc_check=fail` 的报价单照常进入比价界面，只是在界面上高亮警示，由用户在查看时决定是否需要修正。

## 六、对比维度：抽屉机制

对比维度与报价结构**完全解耦**。报价结构只管忠实记录；对比时的"抽屉"（把原子工艺打包成对比桶）是独立的一层：

**内置三个独立维度**（注意：三者是**平行的三种视角**，无层级关系）：工艺域（34 桶）、工艺阶段（12 桶）、工艺类别（3 桶），开箱即用。对比时任选一个维度切抽屉，也可随时切换。

**用户自定义维度**：主数据表 `dim_group`（对比分组）：group_code / group_name / parent_code（支持多层级抽屉）/ member_atoms / scope（全局或指定品类）。自定义抽屉与内置维度可混用；一条原子可属于多个抽屉；未匹配与"其它工艺"条目归入各自专桶，金额始终可见。

**非加工费模块的对比**：按模块合计逐层级横向对比（材料费/检验费/包运费/损管利税/其他/模治具），需要时下钻明细——不需要维度抽屉，只有加工费用抽屉。

## 七、人工介入方式（v1.1 流程变更）

**取消"确认台作为比价前置环节"**。实际流程：

1. LLM 解析完成 → 报价单状态 `parsed` → **直接进入比价界面**（人看到的第一个界面就是比价）
2. 比价界面中，低置信度条目、勾稽异常、未匹配条目以徽标/高亮提示，**不阻断查看**
3. 用户发现问题 → 就地修改（改选原子下拉、修金额、补字段）→ 保存后 JSON 与关系表同步更新，状态转 `reviewed`
4. `is_new_process=true` 的条目 → 前端弹出新工艺决策卡片 → 用户一键新增原子或归并到现有原子（自动回流别名）
5. 每次人工修正触发别名回流：`match_path=manual` 的原文写法自动进入 `atom_alias`（来源=人工回流）
