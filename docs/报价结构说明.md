## 一、数据流总原则：JSON 先行，落库殿后

```
LLM 解析输出 (JSON)
   → 按 quote_schema.json 校验
   → 加工费原子匹配、指纹生成、勾稽计算（全程在 JSON 上处理）
   → 直接进入比价界面（★ 无人工确认前置环节）
   → 用户在比价界面中发现问题 → 就地修改（改的还是这份 JSON）
   → JSON 原样存档（raw_json，审计与重解析用）
   → 同时拍平派生写入关系表（quote / quote_line / tooling_line，供对比查询）
```

JSON 是**处理的基准形态**，关系表是**查询的索引形态**。

### 1.1 信封结构：单文件多产品 / 多报价方案

实际报价单可能一份文件含多个产品（如模具报价单 + 多零件成本表），或同一产品多个报价方案（不同工艺路线各一行报价）。LLM 解析输出统一为**信封结构**：

```
{"offers": [ <quote_schema v1.1 对象>, ... ]}
```

- offers 按 **产品 × 报价方案** 拆分：同产品多方案 → 每行一个 offer，用 `basic.scheme` 区分方案；多产品 → 每产品（每方案）一个 offer。
- 普通报价单只有 1 个元素。`quote_schema.json` 描述的是单个 offer，信封由校验代码程序化包装。
- 落库时每个 offer 独立成一行 `quote`（共享 `file_hash`，比价视图中表现为同一供应商的多个报价列）；信封原文另存 `envelope_<hash>.json` 供查重复用。
- 模治具费用按部品名称归属到对应 offer；整单共用的放入每个相关 offer 并在 note 标注"共用"。

## 二、其它信息字段（other_info）

解析的职责不止于"填满 Schema 字段"。报价单里大量影响决策的内容并不在 `basic`/`unit_price`/`tooling` 的字段定义内——例如付款方式与账期、报价有效期、运费承担与范围、模具付款比例与穴数/寿命条款、包装与标识要求、认证与合规说明、生产周期与产能说明、特殊约束（原料调价重议、报价有效期、起订门槛）等。这些内容统一收敛到顶层字段：

```
other_info: string | null     ← markdown 文本，按主题分点归纳
```

规则：

- **保留判断标准**：凡是"影响采购决策、但 Schema 里没有对应字段"的识别结果，都写进 `other_info`；Schema 里已有字段的内容不重复记录。
- **markdown 格式**：用 `### 小标题` + `- 条目` 组织，便于前端渲染与 LLM 阅读；无法归类的内容放在末尾"其他"。
- **禁止记录敏感信息**：手机号、联系人姓名、邮箱、印章内容等个人身份与签章信息，以及银行账号、开户行、开户资料等收款与开户信息，一律不保留（解析 prompt 内含自检项 `_self_check.other_info_excludes_sensitive_data`）。
- **不做编造**：没识别到就留 `null`；识别到但表述含糊的，照原文措辞记录。
- **不参与金额勾稽**：`other_info` 不进入任何合计计算，纯补充信息。

落库对应 `quote.other_info`（TEXT）。用途有二：① 报价单解析结果详情页直接展示；② **作为 AI 分析模块的补充信息源**——AI 分析拿到的是结构化数据 + 各家 `other_info`，从而能判断"账期未明""运费出省模糊""模具全预付占用资金"这类无法从数字里读出的优劣（见《报价对比Agent-架构设计.md》§五）。

## 三、全层级金额原则（v1.1 核心变更）

供应商可能只报模块总价而没有明细（如"包装运输费 0.08 元/pcs"一条，包装、运输拆不开）。因此**每个层级都有自己的金额字段**：

```
最终含税单价 final_unit_price_taxed          ← 产品单价级总额（对比第一基准）
├─ materials.total          材料费合计        ─┐
├─ processing.total         加工费合计         │
├─ inspection.total         检验费合计         │ 模块级合计：都有 total 字段
├─ packaging_transport.total 包装运输费合计    │ 供应商只报模块价时 items 为空
├─ sga_tax.total            损管利税合计       │
├─ other.total              其他费用合计      ─┘
│   └─ items[]              各模块明细条目（有就填，没有就空）
└─ tooling.total            模治具总合计（元/项，一次性）
    ├─ molds.total / items[]     模具费合计 + 明细
    ├─ fixtures.total / items[]  治具费合计 + 明细
    └─ stencils.total / items[]  钢网费合计 + 明细
```

**total 与 items 的取值规则**：
- 供应商只报合计 → 填 total，items 为空数组
- 供应商报了明细没报合计 → total 留 null，展示层按 Σitems 计算显示（明细里有 null 金额时见下方"下限"规则）
- 两者都有 → **模块合计应 ≥ 明细之和**（供应商可能在合计中包含未逐项列出的内容，不等于明细之和是常态）；若合计 < 明细之和则判为勾稽异常。对比取值优先级：total > Σitems

**单据未印出的金额一律 null（v1.3 核心纪律）**：
- 明细 `amount_per_pc`、各模块 `total`、模治具明细 `amount` 在 Schema 中都是 `["number","null"]`——**允许为 null 是有意为之**：供应商常有"只报模块价不拆明细""报了料重料价但没印材料费"这类情况，此时**必须填 null**。
- **禁止 0 占位、禁止推算**：填 0 会让"缺失"伪装成"免费"；按其它字段算出来的数字（如"料重 28 × 料价 0.96"不得填 26.88）等于编造，二者都是比价层面的严重误导。
- **留证据**：金额留 null 时把相关要素原文照抄进条目 `note`（如「料重 28 / 料价 0.96，材料费未印出」），并在 `_self_check.null_fields` 登记路径，让人一眼看出缺的是什么、能不能自己判定。
- 唯一仍必填的金额字段是 `final_unit_price_taxed`（对比第一基准，缺它整单无法进比价）；`sga_tax` 的税费条目按 `rate` 派生，`amount_per_pc` 天然可为 null。
- **下游对 null 的处理**：`Σitems` 按 0 计入；`derive` 回填模块 `total` 时按下面两条区分（记一条 `amount_missing` 勾稽冲突 → 落库打 `calc_abnormal` 标，界面提示"金额缺失"）：
  - 明细金额**部分**未印出 → 模块 `total` = 已知项之和，**只是下限**（界面照常显示金额，靠 `calc_abnormal` 提示缺项）；
  - 明细金额**全部**未印出 → 模块 `total` 保持 **null**（无任何已知项，Σitems 恒为 0，写 0 就是拿 0 占位）；`module_total()` 对"明细全 null"的模块同样返回 null。
  - **例外：材料栏只印「料价」时由 `derive` 规则 D 兜底**。报价单材料栏常只有「料重 / 料价」两列、没有材料费金额列——此时 LLM 依上面纪律填 null（**它做对了**），但料价本身往往就是每件材料费，白丢一笔钱会让整单勾稽失败。规则 D 因此在**有勾稽背书**时把料价**照抄**为 `amount_per_pc`（只照抄，不做任何乘除，绝不产生「28 × 0.96 = 26.88」）：
    - 背书条件：把候选料价计入后，`(未税 + 按税率估算的税额 − 折扣)` 与单据 `final_unit_price_taxed` 之差 ≤ **0.05 元/pcs**（与勾稽异常口径一致）；
    - 通过 → 照抄料价，`note` 追加「派生值：料价照抄为每件材料费（勾稽背书通过）」，并在 `_derived.material_price_fallback` 留痕（LLM 原值另存于 `_derived.summary_llm_original` 便于追溯）；
    - 不通过（料价其实是 元/kg 单价、单据没印含税单价等）→ 保持 null，照常按上面的缺项规则记 `amount_missing`（`calc_abnormal`），**另**记一条 `material_price_uncorroborated` 冲突说明"为什么没有兜底"。
  前端 null 渲染为「/」（不是 0、不是空白）。

**对比界面按层级展开**：第一屏只看各模块合计的横向对比；每个带明细的行都有 **+/− 折叠/展开按钮**，用户按需展开某模块看明细条目；加工费模块可再按维度抽屉切换视角（见第七节）。

## 四、生产加工费模块（统一结构，全品类通用）

条目字段：`名称(原文) / 金额(元/pcs) / 原子编码 / is_new_process / 打包标志 / 候选原子列表 / 组合指纹 / 拆分方式 / 置信度 / 匹配路径 / 确认状态 / 说明 / 原文出处`

- **不做每品类独立结构**；品类差异由原子清单的品类标签表达。
- 金额无论匹配与否永远保留；未匹配 = `atom_code: null`。
- **清单外新工艺**：工艺不在清单中时，`atom_code = null` + `is_new_process = true`（不再设"其它工艺"兜底原子），金额正常参与加工费合计与总价勾稽，不因"清单外"而丢失。
- **新工艺上报**：`is_new_process = true` 的条目触发 Agent 在前端向用户提问"是否新增原子工艺"（详见架构文档 §六）。
- 打包项：`bundle_flag=true`，按组合指纹跨供应商对齐，不强行估拆。

## 五、损管利税模块

损耗、管理费、利润、税费合为一个模块 `sga_tax`，条目用 `item_type` 标注；供应商合并报价时一条条目即可，不强拆；按百分比报的用 `rate` 保留原费率；税费条目 `rate` 必填。模块只有总价时同样只填 `sga_tax.total`。

## 六、勾稽规则（校验层依据）

```
模块合计取值优先级：模块 total 字段 > Σ 模块 items
模块内部勾稽：模块 total ≥ Σ 模块 items（合计可含未单列内容；total < Σitems 判为异常）
未税合计 untaxed_total  = Σ 六个模块合计（排除 sga_tax 中 item_type=税费 的金额）
含税合计 taxed_total    = untaxed_total + tax_amount
最终含税单价            = taxed_total − discount
```

- 勾稽允差 ±0.01 元或 ±1%。
- **明细金额缺失（null）**：`Σitems` 按 0 计入，模块合计只是**下限**（明细全部未印出时模块合计保持 null，不写 0）；`derive` 对此记一条 `amount_missing` 冲突（derived 侧为按 0 求和的结果），落库打 `calc_abnormal` 标，防止"看起来勾稽通过"的误判。
- **料价兜底（规则 D，先于税额派生）**：材料栏只印料价、没有材料费金额列时，用料价候选做勾稽背书（`未税+估税−折扣` vs 单据含税单价，允差 **0.05 元/pcs**），通过才把料价照抄为每件材料费并把材料栏从缺项名单里摘掉（详见第三节 null 规则的例外）。
- **勾稽失败不阻断流程**：`calc_check=fail` 的报价单照常进入比价界面，只是在界面上高亮警示，由用户在查看时决定是否需要修正。

## 七、对比维度：抽屉机制

对比维度与报价结构**完全解耦**。报价结构只管忠实记录；对比时的"抽屉"（把原子工艺打包成对比桶）是独立的一层：

**内置三个独立维度**（注意：三者是**平行的三种视角**，无层级关系）：工艺域（34 桶）、工艺阶段（12 桶）、工艺类别（3 桶），开箱即用。对比时任选一个维度切抽屉，也可随时切换。

抽屉本身**落库成表** `drawer`（code / name / is_builtin / sort_order），比价界面的抽屉页签由该表驱动——因此新增一个抽屉就等于多一个对比视角：

- **内置抽屉**（工艺类别/工艺阶段/工艺域）`is_builtin=1`，**不可修改、不可删除**；
- **自定义抽屉**可在"基础数据维护 → 抽屉管理"中增删改，可改名称与顺序；删除前须先处置其下的分组。

**用户自定义维度**：主数据表 `dim_group`（对比分组）：group_code / group_name / parent_code（支持多层级抽屉）/ member_atoms / scope（指定所属抽屉，或 `custom` 表示不归属任何内置维度）。自定义抽屉与内置维度可混用；一条原子可属于多个抽屉；清单外与未匹配条目统一归入"未匹配"专桶（始终排在最后），金额始终可见。

**非加工费模块的对比**：按模块合计逐层级横向对比（材料费/检验费/包运费/损管利税/其他/模治具），需要时下钻明细——不需要维度抽屉，只有加工费用抽屉。

## 八、人工介入方式（v1.1 流程变更）

**取消"确认台作为比价前置环节"**。实际流程：

1. LLM 解析完成 → 报价单状态 `parsed` → **直接进入比价界面**（人看到的第一个界面就是比价）
2. 比价界面中，低置信度条目、勾稽异常、未匹配条目以徽标/高亮提示，**不阻断查看**
3. 用户发现问题 → 就地修改（改选原子下拉、修金额、补字段）→ 保存后 JSON 与关系表同步更新，状态转 `reviewed`
4. `is_new_process=true` 的条目 → 前端弹出新工艺决策卡片 → 用户一键新增原子或归并到现有原子（自动回流别名）
5. 每次人工修正触发别名回流：`match_path=manual` 的原文写法自动进入 `atom_alias`（来源=人工回流）
